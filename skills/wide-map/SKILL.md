# 넓은 지도

구현 범위는 명세대로 좁게 두고, 학습 범위는 넓힌다. 질문을 명세에서만 뽑고 흐름 지도가 서버 안쪽만 그리면, 배우는 것도 그 상자 안에 갇힌다. (미니 웹서버: TLS가 어디서 풀리는지, 프록시 뒤의 신뢰 경계, 이벤트 모델을 보지 못함)

## 범위 시작 (흐름 지도 전에)
1. **바깥 지도.** 이 종류의 시스템이 실제 운영에서 놓이는 자리를 한 장에 그린다.
   - 클라이언트부터 저장소까지, 경계(네트워크 · 프록시와 TLS 종료 · 프로세스 · 디스크)를 상자로 나눈다
   - 우리가 만드는 상자를 표시한다. 명세가 뺀 것(TLS, 로드밸런서 등)도 그리고 "이번에 안 만듦"으로 표시한다
   - 공격자와 장애가 서는 자리를 경계 위에 표시한다
2. **실무 질문 3~5개.** 렌즈(공격자 · 규모 · 장애 · 대안 · 비용)별로 현업이 이 시스템에 묻는 질문을 질문 지도의 "실무 질문" 절에 적는다.
   - 구현할 결정이 아니라 탐구할 질문이다. "묻기" 개수에 세지 않는다
   - AI가 질문마다 3~5줄로 답하고, 바깥 지도의 어느 경계인지 짚는다. 사람이 다 읽는 데 10분 안쪽
3. **깊게 팔 1개.** 실무 질문 중 하나를 사람이 고른다. 바깥 지도에 `[깊게]`를 붙인다.
   - 추천 기준: 이번 범위의 묻기 결정과 맞닿은 것 (예: 스레드 풀을 고를 범위라면 느린 연결 공격)
   - 이 항목은 이 범위 안에서 explain-back 대상 1건이 된다. 예측 질문 1개로 메커니즘까지 확인한다
4. 3번이 닫히면 흐름 지도와 질문 지도로 간다.

## 범위 끝 (마지막 단계 점검 때)
1. **실제 시스템 비교표.** 이 범위의 핵심 묻기 결정 1~2개에 대해, 우리 방식과 실제 시스템 2~3개를 표 하나로 놓는다.
   - 열: 방식 · 같은 상황(렌즈 하나로 정한 부하나 공격)에서의 결과 · 그 시스템이 그렇게 고른 이유
2. 표 아래 한 줄: 우리 방식이 맞는 조건과 바꿔야 하는 조건.
3. 측정하지 않은 결과에는 `[예측]`을 붙인다. 출처가 있으면 한 줄로 적는다.

## 위치
- 바깥 지도와 비교표: `docs/flow-map.md`의 "바깥 지도" · "실제 시스템 비교" 절. 새 파일을 만들지 않는다
- 실무 질문: 질문 지도의 "실무 질문" 절
- 채팅에서 쓸 때는 파일 없이 답변에 바깥 지도 · 실무 질문 · 비교표를 바로 낸다

## 하지 않는 것
- 실무 질문을 이번 구현 범위로 끌어오지 않는다. 만들고 싶으면 사람이 다음 범위로 정한다
- 넓게 늘어놓기만 하지 않는다. `[깊게]` 1개가 확인되지 않았으면 범위가 끝난 게 아니다

## 조사를 다른 AI에 맡길 때
바깥 지도와 비교표 조사는 개념 리서치용 AI에 맡겨도 된다. 받은 결과는 그대로 옮기지 않는다. 숫자와 동작 주장에는 출처나 `[예측]`이 있어야 한다.

```
[시스템 종류]를 만든다. 이번 구현 범위: [한 줄]. 구현이 아니라 넓게 이해하려는 조사다.
1. 이 시스템이 실제 운영에서 놓이는 자리를 클라이언트부터 저장소까지 경계 단위로 설명해 줘. 경계마다 무엇이 바뀌는지(프로토콜, 신뢰, 자원).
2. 경계마다 대표적인 공격 또는 장애 1개와, 보통 어느 계층에서 막는지.
3. [핵심 결정, 예: 동시성 모델]에 대해 실제 시스템 2~3개의 방식과, 같은 부하에서 결과가 어떻게 다른지.
4. 주장마다 출처(공식 문서 · RFC · 소스 코드)나 "추정" 표시.
항목당 3~5줄.
```

## 예시 (웹 서버, 기본 구현 범위)

바깥 지도
```
브라우저 → DNS → [LB · nginx: TLS 종료] → [우리 서버: 평문 HTTP] → 정적 파일 · CGI
                  (이번에 안 만듦)
 ↑ 같은 와이파이 도청자        ↑ 느린 연결 공격자 [깊게]      ↑ ../ 경로 공격
                               ↑ 프록시가 붙인 클라이언트 IP를 믿어도 되나
```

실무 질문
- 공격자: 느리게 보내는 연결 몇 개면 서버가 멈추나 → 우리 서버 경계 `[깊게]`
- 공격자: HTTPS로 바꾸면 우리 서버 코드는 무엇이 바뀌나 → TLS 종료 경계
- 규모: 동시 연결 1만 개면 무엇이 먼저 바닥나나 → 프로세스 경계
- 장애: 워커 스레드 하나가 죽으면 그 연결과 나머지는 → 프로세스 경계
- 대안: 실제 웹 서버는 동시 연결을 어떻게 받나 → 범위 끝 비교표로

범위 끝 비교표 (렌즈: 느린 연결이 많을 때)
| 시스템 | 방식 | 결과 | 그렇게 고른 이유 |
|---|---|---|---|
| 우리 서버 | 스레드 풀 + 블로킹 I/O | 워커 수만큼 연결이 묶이면 멈춤 | 코드가 단순, 과제 부하에 충분 |
| Apache prefork | 연결마다 프로세스 | 프로세스 수 한도와 메모리가 먼저 바닥 `[예측]` | 프로세스 격리, 스레드 안전하지 않은 모듈 지원 |
| nginx | 이벤트 루프(epoll) | 연결 수 한도까지 버팀 `[예측]` | 연결이 많고 처리가 짧은 프록시 용도 |
| Go net/http | 연결마다 고루틴 | 버팀. 블로킹 코드처럼 써도 런타임이 이벤트로 바꿈 `[예측]` | 단순한 코드와 많은 연결을 같이 얻음 |

우리 방식이 맞는 조건: 연결 수가 워커 수의 몇 배 안쪽이고, 앞단 프록시가 느린 연결을 걸러 줄 때. 바꿔야 하는 조건: 서버가 인터넷에 직접 노출될 때.
