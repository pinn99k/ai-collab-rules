# 단계 점검

사람이 직접 볼 곳을 고르는 점검이다. 수치는 경보로만 쓰고, 고칠지는 사용자가 정한다.
단계가 끝날 때 한 번 한다. 짧은 프로젝트에서는 "매주"가 오지 않지만 단계의 끝은 반드시 온다.

## 할 일
1. 측정한다. 도구 결과 전문 대신 요약 수치만 대화에 가져온다.
   - 장황성 = 중복 줄 수 / 전체 LOC (jscpd 리포트의 중복 비율)
   - 침식도 = CC 10 초과 함수의 mass 합 / 전체 함수 mass 합, mass = CC × √NLOC (`lizard --csv`의 NLOC, CCN 열로 계산)
   - 도구가 없으면 설치 방법(`pip install lizard`, `npx jscpd`)을 안내하고 멈춘다.
2. `docs/quality-trend.md`에 한 줄 추가한다: `날짜 | 단계 | LOC | 장황성 | 침식도`. 지난 단계의 기록과 비교한다.
3. 단순화 후보 상위 3개를 제시한다: 함수, 수치, 왜 복잡한지 1줄.
4. ARCHITECTURE.md의 규칙과 실제 코드가 다른 곳을 보고한다.
5. 문서(README · `docs/`)에 남은 `[예측]` 수를 보고한다. 측정으로 바꿀 수 있는 것은 측정 방법 한 줄을 붙인다.
6. 흐름 지도(`docs/flow-map.md`)가 실제 코드와 맞는지 확인한다. 다르면 고치고, 이번 단계에서 새로 생기거나 바뀐 화살표를 보고에 넣는다. `[위임]` · `[알려줌]` 표시가 빠진 화살표가 있으면 붙인다. 흐름 지도가 없으면 만들자고 제안한다.
7. 이번 단계의 확인 1건을 고르고 바로 묻는다 (explain-back 스킬 "대상 고르기"). 사용자가 미루면 `대기`로 적는다.
8. 범위의 마지막 단계면 wide-map 스킬의 "범위 끝"(실제 시스템 비교표)을 한다. 흐름 지도의 바깥 지도 절이 비어 있거나 `[깊게]` 항목이 아직 확인되지 않았으면 보고한다.
9. 보고에 넣는다: explain-log 대기 수, 이번 단계 건너뜀(이유 포함), 위임 비율(이번 단계 묻기 중 위임 수).
10. 사용자가 고른 후보만 별도 커밋으로 단순화한다.

## 해석
- 절대값보다 추세를 본다. 수치가 올랐으면 원인 커밋을 찾아 함께 보고한다.
- 참고값 (외부 글 SlopCodeBench, 미검증): 사람이 관리한 저장소는 장황성 약 0.15, 침식도 약 0.31. AI 생성 코드는 약 2배.

## 보고 예시
```
단계 점검 2026-11-13 (Phase 1)
LOC 2,140 (+610) | 장황성 0.18 (+0.03) | 침식도 0.42 (+0.11)

단순화 후보
1. Parser.parseCommand — CC 17, NLOC 64: 명령별 분기가 한 함수에 몰림
2. Store.set — CC 12, NLOC 40: 만료·덮어쓰기·타입 검사가 섞임
3. Server.handle — CC 11, NLOC 52: 에러 처리가 경로마다 다름

남은 [예측] 1건: README "id 조회는 B+트리 때문에 차이 없음" → k6 3회 중앙값으로 확인
흐름 지도: 새 화살표 2개 (#6 만료 확인 [위임 Q2], #7 응답 캐시 [알려줌]), 예정과 다름 1곳 (#4 락 위치)
ARCHITECTURE 불일치: 에러는 예외로 처리하기로 했으나 Store.set이 null을 반환

이번 단계 확인: 흐름 #6 만료 확인 [위임 Q2] → 지금 묻습니다
explain-back 대기 0건 | 건너뜀 0 | 위임 1/2
```
