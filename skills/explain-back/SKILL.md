# explain-back

사용자가 책임질 코드를 스스로 설명할 수 있게 만든다. 모드와 상관없이 항상 쓴다.

## 할 일
1. 대상의 위치와 범위만 알려 준다 (파일, 함수, 커밋). 설명은 먼저 하지 않는다. 먼저 설명하면 사용자는 따라 읽기만 한다.
2. 사용자에게 두 줄을 요청한다.
   - 왜: 왜 여기서 이렇게 했는가
   - 파급: 이걸 바꾸면 어디가 깨지는가
3. 피드백한다: 맞은 점 1줄 → 틀리거나 빠진 메커니즘 → 빠진 영향 범위. 해설은 틀린 부분에만 붙인다.
4. 설명이 막힌 원인이 코드 쪽(불필요한 분기, 숨은 결합)이면 단순화 방안을 제안한다.
5. `docs/explain-log.md`에 한 줄 남긴다: `날짜 | 대상 | 통과·보완·건너뜀 | 메모`. "대기" 항목이었다면 그 줄을 갱신한다.

사용자가 건너뛰면 "건너뜀"으로 기록하고 넘어간다. 건너뛴 비율은 주간 점검에서 본다.

## 무작위 검사 (하루 1건)
그날 explain-log에 무작위 항목이 없으면, 그날 커밋 중 하나를 골라 제안한다.

## 예시
AI: 대상은 `store/Expiry.java`의 `isExpired()`와 `Store.get()` 변경입니다 (커밋 a1b2c3). 두 줄로 설명해 주세요.

사용자:
- 왜: 조회할 때 만료를 확인해서 지우려고 get에 넣었다.
- 파급: 만료 시간 단위를 바꾸면 isExpired만 깨진다.

AI:
- 맞은 점: 조회 시 삭제라는 흐름은 정확합니다.
- 빠진 영향: `exists()`와 `keys()`는 만료 확인을 거치지 않습니다. 그래서 만료된 키가 keys 결과에 그대로 보입니다.
- 판정: 보완

기록: `2026-11-06 | a1b2c3 Expiry | 보완 | keys·exists 만료 확인 누락`
