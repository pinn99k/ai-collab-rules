# explain-back

사용자가 책임질 시스템의 동작을 스스로 예측할 수 있게 만든다. 사용자는 코드를 줄 단위로 읽지 않는다고 가정한다. 예측하고, 돌려 보고, 빗나간 곳에서 메커니즘을 배운다.

## 언제, 몇 건
- 단계가 끝날 때 1건. phase-audit이 고르고 그 자리에서 묻는다. 단계 수가 곧 확인 수다. 큰 개발 범위는 단계가 많아서 확인도 많아진다
- 사용자가 미루면 `대기`로 적는다. 한 단계까지는 미룰 수 있다. 대기가 한도(기본 1건)를 넘으면 커밋 훅이 커밋을 막는다
- 그 밖에 사용자가 원할 때 언제든

마감이 없으면 대기는 쌓이기만 한다(v0.3까지 네 프로젝트 누적 완료 0건). 만들기에는 다음 스텝이라는 마감이 있고 이해에는 없었다. 단계 끝과 커밋 차단이 그 마감이다.

## 대상 고르기 (단계마다 1개)
그 단계에서 생기거나 바뀐 흐름 지도 화살표 중에서 고른다. 우선순위:
1. `[위임 Qn]` 표시 화살표: 사용자가 고르지 않은 결정
2. `[알려줌]` 표시 화살표: AI가 정한 작동 원리
3. 그 단계의 묻기 결정이 기대는 메커니즘 (예: 스레드 풀을 골랐다면 워커가 다 찼을 때 일어나는 일)

1건에는 개념 1개만 담는다. 대상에 화살표 번호를 붙인다. 예: `흐름 #5 연결 마감 시간`.

## 할 일
1. 상황을 주고 관찰 가능한 결과를 묻는다. 코드를 보라고 하지 않는다. 설명은 먼저 하지 않는다. 먼저 설명하면 사용자는 따라 읽기만 한다.
   - 좋은 질문: 답이 하나로 정해지고, 명령 하나(`curl`, `wrk`, 테스트)로 확인된다. "이 상황이면 무엇이 몇 번 / 몇 ms / 몇 번째에 일어날까?"
   - 정상 동작만 묻지 않아도 된다. 렌즈(공격자 · 장애 · 규모)로 상황을 만들면 넓게 본다. 예: "느리게 보내는 연결 8개를 열어 두면 9번째 요청은?"
2. 사용자가 답하면 실행한다. 실행할 수 없으면 근거가 되는 흐름 지도 화살표를 짚는다. 맞으면 통과다.
3. 틀리면 빗나간 지점의 메커니즘만 해설한다. 화살표 번호로 짚고, 코드 위치는 마지막에 참고로 한 줄 붙인다.
4. 막힌 원인이 구조 쪽(불필요한 분기, 숨은 결합)이면 단순화 방안을 제안한다.
5. 기록한다.

사용자가 건너뛰면 `건너뜀`과 이유 한 줄을 적는다. 이유 없는 건너뜀은 적지 않는다(대기로 남긴다). 건너뜀 비율은 단계 점검이 보고한다.

## 기록 형식 (`docs/explain-log.md`)
```
날짜 | 단계 · 대상 | 대기·통과·보완·건너뜀·보관 | 메모
```
- 통과: 예측이 맞음 / 보완: 틀려서 해설을 들음 / 건너뜀: 하지 않고 닫음, 이유 필수
- 보관: v0.3 이전에 쌓인 대기를 닫지 않고 치운 것. 훅이 세지 않는다

## 예시
대기: `2026-11-24 | Phase 2 · 흐름 #3 Nagle + 지연 ACK [알려줌] | 대기 |`

AI: keep-alive 연결 하나로 작은 요청 100개를 차례로 보냅니다. TCP_NODELAY를 끈 상태입니다. 100개가 끝나는 데 대략 얼마나 걸릴까요? 서버 처리 시간은 요청당 1ms 미만입니다.

사용자: 0.1초 정도.

AI:
- 실행 결과(`wrk -c1 -d5s`)는 요청당 약 40~50ms, 100개에 4~5초입니다.
- 빗나간 지점: 흐름 #3. 서버가 응답을 두 번에 나눠 쓰면, 두 번째 조각은 첫 조각의 ACK를 기다립니다(Nagle). 클라이언트는 ACK를 모아 보내려고 늦춥니다(지연 ACK). 서로 기다리는 시간이 요청마다 붙습니다.
- 참고 위치: 응답을 쓰는 함수 (예: `conn.c`의 `send_response`)
- 판정: 보완

기록: `2026-11-24 | Phase 2 · 흐름 #3 Nagle + 지연 ACK [알려줌] | 보완 | 응답을 두 번 쓰면 ACK 대기가 요청마다 붙음`
