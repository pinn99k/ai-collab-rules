# explain-back

사용자가 책임질 코드의 동작을 스스로 예측할 수 있게 만든다. 강제하지 않는다. 대기 수는 커밋 훅이 한 줄로 보여 준다.

## 대상
- 사용자가 "추천대로"로 넘긴 결정 (위임)
- AI가 정했지만 시스템이 기대는 작동 원리
- 커밋 훅의 품질 경보가 울린 diff

사용자가 직접 고른 결정은 대상이 아니다. 고르는 과정에서 이미 확인했다.
대기 1건에는 개념 1개만 적는다. 둘 이상이면 나눠 적는다. 한 건이 크면 시작하기 어렵다.

## 할 일
1. `docs/explain-log.md`의 대기 항목 하나를 골라 예측 질문 1개를 낸다. 설명은 먼저 하지 않는다. 먼저 설명하면 사용자는 따라 읽기만 한다.
2. 예측 질문은 답이 하나로 정해지고 실행으로 확인할 수 있어야 한다. 예: "이 상황이면 무엇이 몇 번 일어날까?"
3. 사용자가 답하면 실행하거나 코드를 짚어 확인한다. 맞으면 통과다. 틀리면 틀린 지점만 해설한다.
4. 사용자가 원하면 두 줄(왜 이렇게 했는가 / 바꾸면 어디가 깨지는가)로 정리해 보게 한다. 선택이다.
5. 막힌 원인이 코드 쪽(불필요한 분기, 숨은 결합)이면 단순화 방안을 제안한다.
6. 대기 줄을 결과로 바꾼다.

사용자가 건너뛰면 "건너뜀"으로 기록하고 넘어간다. 건너뛴 비율은 단계 점검에서 본다.

## 기록 형식 (`docs/explain-log.md`)
```
날짜 | 대상 | 대기·통과·보완·건너뜀 | 메모
```
- 통과: 예측이 맞음 / 보완: 틀려서 해설을 들음 / 건너뜀: 하지 않고 닫음

## 예시
대기: `2026-11-06 | Store.get의 만료 처리 (위임) | 대기 |`

AI: `store/Expiry.java`의 `isExpired()`와 `Store.get()`을 봐 주세요. 만료 시간이 지난 키가 3개 있습니다. 아무도 조회하지 않은 채로 `keys()`를 부르면 몇 개가 나올까요?

사용자: 0개. 만료됐으니까.

AI:
- 실행 결과는 3개입니다.
- 틀린 지점: 만료 확인은 `get()`에만 있습니다. `keys()`와 `exists()`는 만료 확인을 거치지 않습니다.
- 판정: 보완

기록: `2026-11-06 | Store.get의 만료 처리 (위임) | 보완 | keys·exists는 만료 확인을 안 거침`
