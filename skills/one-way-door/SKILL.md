# 한쪽 문 결정

되돌리기 비싼 결정은 사용자가 내린다. 이 스킬은 결정 재료를 카드 한 장으로 줄이고, 결정을 기록으로 남긴다.

## 해당 여부
모든 모드:
- 자료구조, 저장 포맷, 스키마
- 프로토콜, 공개 API 형태
- 모듈 경계 변경, 새 모듈
- 외부 의존성 추가
- 새 패턴 도입: 다른 코드가 따라 쓰게 될 방식 (다음 세션이 그 패턴을 복제해 퍼뜨린다). 파일 하나 안에서 끝나는 도우미는 해당하지 않는다
- 기존 ADR과 다른 방향

learning 모드에서 추가:
- 동시성 모델: 시스템 전체가 따르는 실행 방식 (예: 스레드 풀 vs 이벤트 루프)

핵심 알고리즘 · 에러 처리 · 테스트 전략은 묻지 않는다(v0.4). AI가 정하고 질문 지도에 "알려주기"로 한 줄, 흐름 지도 화살표에 `[알려줌]`을 붙인다. 작은 결정까지 물으면 사람은 도장만 찍는다.

모드는 프로젝트 CLAUDE.md의 `MODE:` 값이다. 없으면 learning.
목록에 없는 결정은 바로 구현하고, 커밋 메시지에 결정을 한 줄 남긴다.
질문 지도에서 "묻기"는 단계당 0~2개다. 넘으면 단계를 나누자고 제안한다.

## 할 일
1. 코드를 쓰기 전에 결정 카드를 내고 답을 기다린다. 질문은 한 번에 하나만 낸다. 프로젝트에 질문 지도(`docs/question-maps/`)가 있으면 그 질문의 카드로 적는다.
2. 답을 받으면 카드에 답 · 누가 정했는지 · 날짜를 적고, `docs/adr/NNNN-<slug>.md`에 ADR을 쓴다. ADR은 기록용이다. 카드의 내용을 옮겨 적고, 사용자에게 읽거나 채우라고 하지 않는다.
3. 사용자가 "추천대로"로 넘기면 추천안으로 진행한다. 답에 `위임`을 적고, 흐름 지도(`docs/flow-map.md`)의 해당 화살표에 `[위임 Qn]`을 붙인다. 위임은 정상 경로다. 단계 끝 explain-back이 이 표시에서 대상을 고른다.
4. 사용자가 직접 고른 결정은 표시하지 않는다. 고르는 과정이 이해 확인이다.
5. ARCHITECTURE.md가 있으면 ADR 목록과 해당 "단일 방식 규칙"을 갱신한다.

## 결정 카드 (7줄 이내)
```
**Q. 정할 것 한 줄**
- A: 이렇게 하면 → 이런 결과
- B: 저렇게 하면 → 저런 결과
- 렌즈1: A는 ~, B는 ~
- 렌즈2: A는 ~, B는 ~
- 추천: A. 이유 한 줄
```
- 선택지는 용어가 아니라 결과로 쓴다. 이름은 사용자가 고른 뒤에 붙인다. 용어를 모르면 고를 수 없기 때문이다.
- 렌즈 2개는 규모 · 장애 · 공격자 · 비용 · 대안 중 이 결정을 가장 크게 가르는 둘이다. 되돌리기 비용이나 유지보수 비용이 선택을 가르면 비용 렌즈로 적는다. 결정한 뒤 터질 곳이 카드에 미리 보여야 한다. 측정 전 숫자에는 `[예측]`을 붙인다.
- 선택지가 넷 이상이거나 비교 축이 여럿이면 카드 아래에 표를 덧붙인다. 카드만 읽어도 고를 수 있어야 한다.

## 예시
상황: 웹 서버 구현 중 동시 연결 처리 방식이 필요하다.

**Q. 동시에 들어오는 연결을 어떻게 처리할까**
- A: 워커 스레드 몇 개가 연결 하나씩 끝까지 맡는다 → 코드가 위에서 아래로 읽힌다. 동시 처리 수는 워커 수까지다
- B: 스레드 하나가 준비된 연결만 골라 조금씩 처리한다 → 연결이 많아도 버틴다. 처리 코드가 상태별로 쪼개진다
- 공격자: A는 느리게 보내는 연결이 워커 수만큼 있으면 전부 묶인다(마감 시간으로 줄인다). B는 연결 수 한도까지 버틴다
- 규모: A는 워커 수를 넘는 연결이 큐에서 기다린다. B는 수천 연결도 스레드 하나로 받는다
- 추천: A. 이 과제의 부하에서는 충분하고, 묶임은 연결 마감 시간으로 줄일 수 있다

사용자가 A를 고른 뒤: "A는 스레드 풀 + 블로킹 I/O, B는 이벤트 루프(epoll)라고 부른다."
