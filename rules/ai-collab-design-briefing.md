# 설계 브리핑

목적: 사람이 흐름 → 질문 → 결정의 순서를 AI와 같이 걸어서, 왜 그렇게 정해졌는지 알게 한다. 사람은 아키텍처급 결정에만 시간을 쓰고, 작은 로직은 AI가 정한 뒤 흐름 지도에 표시한다. 사람이 읽을 것은 줄인다.
출처: mini-react 1주 적용(2026-11-09 트러블슈팅, 11-13 회고), 미니 DBMS 적용(2026-11-17 회고), 미니 레디스 · mini-stack 적용(2026-11-19 회고), 미니 웹서버 적용(2026-11-26 회고). AI가 설계를 끝낸 뒤 물으면 사람은 중간부터 들어가고, 뒤에 쓴 이유는 사후 해설이 된다. 반대로 작은 결정까지 다 물으면 사람은 "추천대로"로 도장만 찍는다(웹서버 위임 14줄).

## 개발 범위와 단계
- 개발 범위: 한 번에 설계 → 구현 → 확인하는 묶음. 예: 기본 구현, 차별점. 프로젝트 하나에 범위가 여러 개일 수 있다
- 범위는 단계(Phase)로 나눈다. 범위가 크면 단계가 많아지고, 질문과 확인 수도 단계 수만큼 늘어난다. 작은 범위는 몇 개 없다
- 질문 수와 확인 수는 고정하지 않는다. 단계당 기준만 둔다 (아래 "묻기", explain-back 스킬)

## 순서
1. 범위를 시작할 때 흐름 지도를 먼저 낸다. 처음 만드는 종류의 시스템이면 그 종류의 일반적인 요청 경로를 모듈 이름으로 그린다. 사람과 한 번 걷는다: 예측 질문 1개를 내고, 맞히지 못해도 된다. 기록하지 않는다. 전체를 먼저 봐야 결정할 수 있다.
2. 질문 지도를 낸다. 명세를 읽고 생기는 질문을 답이 서로 기대는 순서대로 적는다.
3. 사람이 "묻기" 질문을 위에서부터 하나씩 결정한다. AI는 질문마다 결정 카드 1장을 낸다.
4. 답을 지도에 적고 다음 질문으로 간다. 앞 답이 바뀌면 그 아래 질문을 다시 본다.
5. "묻기" 질문이 닫히면 흐름 지도를 답에 맞게 고치고 구현한다.
6. 단계가 끝나면 흐름 지도를 실제 코드 기준으로 고치고, 설계 메모와 ADR을 쓰고, 단계 점검(phase-audit 스킬)을 한 번 한다. 단계 점검이 explain-back 1건을 바로 묻는다.

구현 중에 지도에 없던 아키텍처급 결정(새 패턴 포함)이 필요해지면 멈추고 지도에 질문을 더한다. 파일 하나 안에서 끝나는 도우미는 묻지 않는다.

사람이 고민하는 동안 AI는 결정과 무관한 준비(테스트 틀, 폴더 구조, 다음 카드)만 한다. 아직 안 닫힌 질문에 기대는 코드는 쓰지 않는다.

## 사람이 작업 중에 읽는 문서 (두 장)
| 문서 | 답하는 질문 | 틀 · 위치 |
|---|---|---|
| 흐름 지도 (프로젝트에 1장) | 시스템이 실제로 어떻게 돌아가나 | `templates/flow-map.md` · `docs/flow-map.md` |
| 질문 지도 (개발 범위마다 1장) | 왜 이렇게 정했나 | `templates/question-map.md` · `docs/question-maps/` |

사람은 코드를 줄 단위로 읽지 않는다고 가정한다. 이해는 흐름 지도와 실행 결과로 한다. 줄 단위 정확성은 테스트가 맡는다.

### 흐름 지도
- 요청 하나가 들어와서 결과가 나갈 때까지 끝에서 끝까지 한 장에 그린다. 범위와 단계가 나뉘어도 그림은 하나다
- 화살표마다: 파일 · 함수, 그 시점의 데이터 모양, 락이나 상태 변화, 실패하면 나가는 곳, 결정 표시
- 결정 표시: AI가 정한 작동 원리는 `[알려줌]`, 사람이 "추천대로"로 넘긴 결정은 `[위임 Qn]`. explain-back은 표시가 붙은 화살표에서 고른다
- 경로를 나눠 적는다: 쓰기, 읽기, 갈라지는 읽기, 에러
- 단계가 끝날 때 "이번 단계에서 바뀐 것"(새 화살표, 예정과 달라진 곳)을 채팅 브리핑에 넣는다
- 사람이 흐름을 물어볼 때까지 기다리지 않는다. 설명할 때는 흐름 지도의 화살표 번호를 짚는다

### 질문 지도
- 질문마다 적는다: 명세나 받은 설계의 어느 문장에서 나왔는지, 어느 질문의 답에 달렸는지, 등급, 어느 단계인지
- 명세가 이미 정한 것과 고를 수 있는 것을 나눈다. (질문 목록으로 설계를 유도하지 않기 위해)
- "묻기"는 단계당 0~2개. 넘으면 단계가 너무 큰 것이다. 단계를 나누거나, 영향이 작은 것을 "알려주기"로 내린다

## 결정 등급
| 등급 | 대상 | AI가 하는 일 |
|---|---|---|
| 묻기 | 아키텍처급 결정: one-way-door 스킬 목록 (자료구조 · 저장 포맷, 프로토콜 · API, 모듈 경계, 외부 의존성, 새 패턴, 동시성 모델 등) | 결정 카드를 내고 답을 기다린다 |
| 알려주기 | AI가 정했지만 시스템이 기대는 작동 원리. 알고리즘 · 에러 처리 · 테스트 전략 포함 | 지도에 답 한 줄 + 흐름 지도 화살표에 `[알려줌]` |
| 맡기기 | 이름 · 형식 · 함수 나누기 · 분기 처리 등 작은 로직 | 지도에 한 줄만 |

## 결정 카드 (질문 1개 = 카드 1장, 7줄 이내)
- 선택지는 용어가 아니라 결과로 쓴다: "이렇게 하면 → 이렇게 된다". 이름은 고른 뒤에 붙인다. (용어를 모르면 고를 수 없다)
- 렌즈 2개로 선택지를 비교한다. 렌즈는 규모 · 장애 · 공격자 · 비용 · 대안 중 이 결정을 가장 크게 가르는 둘. 넓은 시야는 여기서 본다. 결정한 뒤에 터질 곳이 카드에 미리 보여야 한다
- 추천 1개와 이유 한 줄
- 사람이 "추천대로"로 넘기면 답에 `위임`을 적고, 흐름 지도의 해당 화살표에 `[위임 Qn]`을 붙인다. 위임은 정상 경로다. explain-log에는 바로 넣지 않는다

## 설계를 다른 곳에서 할 때 (채팅 · Cowork → Claude Code)
설계와 구현을 다른 도구에서 해도 된다. 두 쪽이 이 규칙을 같이 쓴다.

설계 쪽:
- 이 파일을 직접 읽고 시작한다. `CLAUDE.md`의 `@` 불러오기가 안 되는 도구도 있다
- 넘기는 것: 흐름 지도, 답이 적힌 질문 지도, 빈칸 목록(설계가 정하지 않고 구현에 남긴 것)

구현 쪽:
- 받은 설계가 정한 것은 다시 묻지 않는다
- 빈칸 중 아키텍처급만 질문 지도에 올려 "묻기"로 하나씩 닫은 뒤 구현한다. 나머지 빈칸은 "알려주기" · "맡기기"로 정한다
- 받은 설계에 질문 지도가 없으면, 받은 설계를 읽고 빈칸 지도를 먼저 만든다. 질문 지도를 끄지 않는다

## 문서를 쓸 때 (README · 발표 · 회고)
코드 설계와 같은 순서로 간다. AI가 초안을 먼저 쓰고 사람이 고치면, 사람은 AI가 정한 독자와 순서를 걷어내는 데 시간을 쓴다.
- 쓰기 전에 세 칸을 사람과 닫는다: 독자(누가 읽나), 한 줄 결론, 말하는 순서
- 세 칸이 닫히기 전에는 본문을 쓰지 않는다. 숫자 · 사실 정리 같은 준비만 한다
- 사람이 고르지 않은 틀(차별점 문구, 비유)은 넣지 않는다

## 기록용 문서 (작업 중에 사람에게 읽으라고 하지 않는다)
- 설계 메모(`templates/design-memo.md`): 단계가 끝날 때 전체 흐름을 서술한다. 프로젝트가 끝난 뒤 브리핑용
- ADR: 결정 · 이유 · 누가 정했는지(사람 / 위임 / AI)만 적고 지도를 가리킨다
- 둘 다 지도의 답을 옮겨 쓴다. 지도와 다르면 지도가 맞다
- 학습 가이드는 만들지 않는다. 흐름 지도가 대신한다. 함수 단위 가이드는 읽는 사람이 없으면 기록 비용만 남는다(웹서버: 빨라지는 구간에서 가장 먼저 빠짐)
- 설계 문서(질문 지도 · 흐름 지도)를 다른 저장소로 넘길 때 복사하지 않는다. 옮기면 같은 커밋에서 원래 자리를 지우고 새 위치 한 줄을 남긴다. 참고만 하면 원본 위치 한 줄만 둔다. 통합 저장소도 같다

## 채팅 브리핑
- 쓰는 것: 결론 1~2줄 · 결정할 것 · 알아야 할 핵심 원리 · 사람이 할 일. 해당 없는 칸은 생략
- 쓰지 않는 것: 한 일 상세 목록 · 파일 목록 · 테스트 수 나열 · 여러 문서 링크. 물어보면 답한다
- 읽을 문서는 흐름 지도와 질문 지도만 가리킨다
