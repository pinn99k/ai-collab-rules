# 설계 브리핑

목적: 사람이 명세 → 질문 → 결정의 순서를 AI와 같이 걸어서, 왜 그렇게 정해졌는지 알게 한다. 그리고 코드가 실제로 어떻게 돌아가는지 묻기 전에 보여 준다. 사람이 읽을 것은 줄인다.
출처: mini-react 1주 적용(2026-11-09 트러블슈팅, 11-13 회고), 미니 DBMS 적용(2026-11-17 회고). AI가 설계를 끝낸 뒤 물으면 사람은 중간부터 들어가고, 뒤에 쓴 이유는 사후 해설이 된다. 전체 흐름은 사람이 물어봐야 나왔다.

## 순서
1. 설계하기 전에 질문 지도와 예정 흐름 지도를 함께 낸다. 질문 지도는 명세를 읽고 생기는 질문을 답이 서로 기대는 순서대로 적는다. 예정 흐름 지도는 요청 하나가 지나갈 길을 모듈 이름으로 그린다. 전체를 먼저 봐야 결정할 수 있다.
2. 사람이 질문을 위에서부터 하나씩 결정한다. AI는 질문마다 결정 카드 1장을 낸다.
3. 답을 지도에 적고 다음 질문으로 간다. 앞 답이 바뀌면 그 아래 질문을 다시 본다.
4. "묻기" 질문이 모두 닫히면 예정 흐름 지도를 답에 맞게 고치고 구현한다.
5. 단계가 끝나면 흐름 지도를 실제 코드 기준으로 고치고, 설계 메모와 ADR을 쓰고, 단계 점검(phase-audit 스킬)을 한 번 한다.

구현 중에 지도에 없던 새 패턴(다른 코드가 따라 쓰게 될 방식)이 필요해지면 멈추고 지도에 질문을 더한다. 파일 하나 안에서 끝나는 도우미는 묻지 않는다.

사람이 고민하는 동안 AI는 결정과 무관한 준비(테스트 틀, 폴더 구조, 다음 카드)만 한다. 아직 안 닫힌 질문에 기대는 코드는 쓰지 않는다.

## 사람이 작업 중에 읽는 문서 (두 장)
| 문서 | 답하는 질문 | 틀 · 위치 |
|---|---|---|
| 질문 지도 (단계마다 1장) | 왜 이렇게 정했나 | `templates/question-map.md` · `docs/question-maps/` |
| 흐름 지도 (프로젝트에 1장) | 코드가 실제로 어떻게 돌아가나 | `templates/flow-map.md` · `docs/flow-map.md` |

### 질문 지도
- 질문마다 적는다: 명세나 받은 설계의 어느 문장에서 나왔는지, 어느 질문의 답에 달렸는지, 등급
- 명세가 이미 정한 것과 고를 수 있는 것을 나눈다. (질문 목록으로 설계를 유도하지 않기 위해)
- "묻기"는 단계당 5개 안팎. 넘으면 영향이 큰 것부터 남기고 나머지는 "알려주기"로 내린다

### 흐름 지도
- 요청 하나가 들어와서 결과가 나갈 때까지 끝에서 끝까지 한 장에 그린다. 단계가 나뉘어도 그림은 하나다
- 화살표마다: 파일 · 함수, 그 시점의 데이터 모양, 락이나 상태 변화, 실패하면 나가는 곳
- 경로를 나눠 적는다: 쓰기, 읽기, 갈라지는 읽기, 에러
- 단계가 끝날 때 "이번 단계에서 바뀐 것"(새 화살표, 예정과 달라진 곳)을 채팅 브리핑에 넣는다
- 사람이 흐름을 물어볼 때까지 기다리지 않는다. 설명할 때는 흐름 지도의 화살표 번호를 짚는다

## 결정 등급
| 등급 | 대상 | AI가 하는 일 |
|---|---|---|
| 묻기 | 한쪽 문(one-way-door 스킬 기준) + 핵심 로직(알고리즘 · 상태 관리 · 데이터 흐름) | 결정 카드를 내고 답을 기다린다 |
| 알려주기 | AI가 정했지만 시스템이 기대는 작동 원리 | 지도에 답 한 줄 + `docs/explain-log.md`에 대기 1건 |
| 맡기기 | 이름 · 형식 · 함수 나누기 등 주변 결정 | 지도에 한 줄만 |

## 결정 카드 (질문 1개 = 카드 1장, 5줄 이내)
- 선택지는 용어가 아니라 결과로 쓴다: "이렇게 하면 → 이렇게 된다". 이름은 고른 뒤에 붙인다. (용어를 모르면 고를 수 없다)
- 추천 1개와 이유 한 줄
- 사람이 "추천대로"로 넘기면 답에 `위임`을 적고 `docs/explain-log.md`에 대기 1건을 넣는다. 위임은 정상 경로다. 표시를 남겨 나중에 볼 곳을 알게 한다

## 설계를 다른 곳에서 할 때 (채팅 · Cowork → Claude Code)
설계와 구현을 다른 도구에서 해도 된다. 두 쪽이 이 규칙을 같이 쓴다.

설계 쪽:
- 이 파일을 직접 읽고 시작한다. `CLAUDE.md`의 `@` 불러오기가 안 되는 도구도 있다
- 넘기는 것: 답이 적힌 질문 지도, 예정 흐름 지도, 빈칸 목록(설계가 정하지 않고 구현에 남긴 것)

구현 쪽:
- 받은 설계가 정한 것은 다시 묻지 않는다
- 빈칸만 질문 지도에 올려 "묻기"로 하나씩 닫은 뒤 구현한다
- 받은 설계에 질문 지도가 없으면, 받은 설계를 읽고 빈칸 지도를 먼저 만든다. 구현하려면 정해야 하는데 설계에 없는 것(쓰기 순서, 에러 처리, 응답 형식 등)을 질문으로 적는다. 질문 지도를 끄지 않는다

## 기록용 문서 (작업 중에 사람에게 읽으라고 하지 않는다)
- 설계 메모(`templates/design-memo.md`): 단계가 끝날 때 전체 흐름을 서술한다. 프로젝트가 끝난 뒤 브리핑용
- ADR: 결정 · 이유 · 누가 정했는지(사람 / 위임 / AI)만 적고 지도를 가리킨다
- 둘 다 지도의 답을 옮겨 쓴다. 지도와 다르면 지도가 맞다
- 학습 가이드: 프로젝트가 끝날 때 한 번만 만든다. 흐름 지도와 결정 기록에서 옮겨 쓴다. 작업 중에는 만들거나 갱신하지 않는다. 사본 문서를 손으로 맞추는 일을 없애기 위해서다

## 채팅 브리핑
- 쓰는 것: 결론 1~2줄 · 결정할 것 · 알아야 할 핵심 원리 · 사람이 할 일. 해당 없는 칸은 생략
- 쓰지 않는 것: 한 일 상세 목록 · 파일 목록 · 테스트 수 나열 · 여러 문서 링크. 물어보면 답한다
- 읽을 문서는 질문 지도와 흐름 지도만 가리킨다

## 규칙 · 문서 구조 변경
- 브리핑 → 사람 승인 → 반영 순서. 승인 전에 파일을 고치지 않는다
