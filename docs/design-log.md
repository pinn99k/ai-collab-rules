## 1. 문제

AI에게 맡기면 구현은 빠르지만, 어디까지 무엇을 왜 만들었는지 따라가지 못했다. 설계 문서, AI가 쓰는 ADR, 기능 단위 개발을 시도했지만 모두 AI가 결정하고 AI가 기록하는 구조라서, 읽어도 이미 내려진 결정의 사후 해설에 그쳤다.

여기에 반복 개발에서 조잡한 코드가 누적되는 문제가 겹친다. 세션이 바뀔 때마다 AI의 맥락이 초기화되고, AI는 기존 코드의 패턴을 복제한다. 그래서 한 번 들어온 이상한 구조가 퍼진다. 결국 책임져야 할 코드를 설명할 수 없게 된다.

목표는 속도를 유지하면서, 어떤 코드든 설명할 수 있는 상태를 지키는 것이다.

## 2. 핵심 원칙

**결정은 문의 종류로 나눈다.** 되돌리기 비싼 결정(한쪽 문)은 사람이 내리고, 기존 패턴 안의 결정(양쪽 문)은 AI가 내린 뒤 기록한다. 다른 코드가 따라 쓰게 될 새 패턴은 작아 보여도 한쪽 문이다. 퍼지기 때문이다. 파일 하나 안에서 끝나는 도우미는 양쪽 문이다(v0.2). 애매하면 한쪽 문으로 본다.

**검사는 회계 감사처럼 세 겹으로 한다.** 전수조사는 하지 않는다. 내부통제(규칙으로 예방), 분석적 절차(도구가 경보), 표본 검사(사람이 고른 곳만 직접 확인)로 나눈다.

**목표는 유도 가능성이다.** 모든 줄을 외우는 것이 아니라, 구조가 일관돼서 처음 보는 코드도 추론할 수 있는 상태다. 그래서 같은 일은 한 방식으로만 한다.

**이해는 예측이 빗나간 데서 생긴다.** 설명을 읽는 것이 아니라 직접 설명해 보고 틀린 곳을 교정받을 때 이해가 생긴다.

## 3. 결정 사항

| 항목 | 결정 |
|---|---|
| 변경 요약 | 커밋 단위 5줄. 숫자는 git이, 이유는 AI가 쓴다 |
| 경보 기준 | 이번 커밋에서 새로 생긴 것만. CC 10 초과, 새 중복, 소스 LOC가 예상의 2배 초과. 테스트끼리의 중복과 테스트 LOC는 제외 (v0.2) |
| 실행 시점 | 매 커밋 직전 git 훅 + 단계가 끝날 때 점검 (v0.2. v0.1은 주 1회) |
| 경보 동작 | 경고만 한다. 차단하면 숫자 맞추기가 목표가 된다 |
| 측정 도구 | lizard(복잡도), jscpd(중복). 모든 언어 공통 |
| explain-back | 예측 질문 1개. 대상은 위임한 결정, AI가 정한 작동 원리, 경보 diff. 강제하지 않고 커밋 훅이 대기 수만 보여 준다 (v0.2) |
| 설계 순서 | 설계 전에 질문 지도를 내고 사람이 하나씩 결정한다. 사람이 읽는 설계 문서는 질문 지도 1장 (v0.2) |
| 모드 | learning / ship. 한쪽 문 범위만 바꾼다 |
| 구성 원칙 | 파일 하나에 목적 하나. 이름에 CLAUDE를 넣지 않는다. 스킬은 혼자서 완결된다 |
| 작성 원칙 | 금지 목록보다 할 일과 이유. 꼭 필요한 금지만 이유와 함께 남긴다 |

## 4. 구성

**md 규칙 (rules/)**: `~/.claude/rules/`에 설치하면 모든 프로젝트에서 매 세션 자동으로 읽는다.
- `ai-collab-coding-discipline`: Karpathy 4원칙 각색 + 일관성
- `ai-collab-change-summary`: 구현 전 예상 1줄, 커밋 요약 5줄
- `ai-collab-quality-alarms`: 경보 기준과 경보가 울렸을 때 할 일
- `ai-collab-design-briefing`: 설계 전 질문 지도, 결정 등급, 결정 카드, 짧은 브리핑 (v0.2)
- `templates/`: 프로젝트에 복사해 쓰는 CLAUDE.md, ARCHITECTURE.md, 질문 지도 틀, 설계 메모 틀

**스킬 (저장 완료)**: 필요할 때만 불러온다. rules/를 참조하지 않는다.
- `one-way-door`: 한쪽 문 판별 기준, 결정 카드 제시, 결정 대기, 위임 표시, ADR 기록
- `explain-back`: 예측 질문 1개로 이해 확인
- `phase-audit`: 단계가 끝날 때 장황성·침식도 측정, 추세 비교, 단순화 후보 제시 (v0.1의 weekly-audit)

스킬끼리는 `docs/explain-log.md`를 공유해 연결된다. 위임한 결정과 경보가 "대기"로 쌓이고, explain-back이 그것을 예측 질문으로 닫는다.

**훅 (hooks/)**: 판단 없이 무조건 실행된다. 경고만 하고, 기록은 `.git/ai-alarms.log`에 남긴다. explain-back 대기 수도 여기서 보여 준다.

## 5. 작업 흐름

1. AI가 명세를 읽고 질문 지도를 낸다. 코드는 아직 쓰지 않는다.
2. 사람이 "묻기" 질문을 위에서부터 하나씩 결정한다. 질문마다 결정 카드 1장. "추천대로"로 넘기면 위임으로 표시한다.
3. AI가 예상 규모를 1줄 적고 구현한다.
4. 커밋 직전 훅이 지표를 측정해 경보를 내고, explain-back 대기 수를 보여 준다.
5. 커밋 요약 5줄을 남긴다.
6. 대기 항목은 예측 질문으로 닫는다 (explain-back).
7. 단계가 끝나면 설계 메모와 ADR에 질문 지도의 답을 옮기고, phase-audit를 한 번 한다.

## 7. 기각한 대안
8. v0.2에서 바뀐 것

- **모든 결정을 사람이 한다**: 구현 속도라는 장점이 사라진다.
- **모든 변경을 ADR로 남긴다**: 문서가 노이즈가 되어 아무도 읽지 않는다. ADR은 한쪽 문만 남긴다.
- **AI가 사고 흐름을 기록한다**: 그럴듯한 사후 합리화가 된다. 결정 이유는 사람이 쓴다.
- **AI에게 품질 점수를 매기게 한다**: 판단이 흔들린다. 경보는 결정론적인 도구가 울린다.
- **경보가 커밋을 차단한다**: AI가 지표 통과 자체를 목표로 삼게 된다.
- **스킬이 외부 md를 참조한다**: 경로가 없는 환경에서 스킬이 빈 껍데기가 된다.
- **커뮤니티 스킬을 그대로 설치한다**: 우리 기준과 맞지 않고, 훅 스크립트 보안 검토가 필요하다. 검증된 문구만 차용했다.
- **AI가 설계를 끝낸 뒤 묻는다 (v0.1, mini-react)**: 사람은 중간부터 들어가서 왜 그 구조가 됐는지 모른다. 뒤에 쓰는 이유는 결론에서 거꾸로 만든 해설이다. 질문 지도로 순서를 뒤집었다.
- **explain-back을 통과해야 진행한다 / 훅이 커밋을 막는다**: 사용자 결정으로 v0.2에는 넣지 않았다. 질문 지도와 강제를 함께 넣으면 어느 쪽 효과인지 알 수 없다.

## 8. v0.2에서 바뀐 것

mini-react에 1주 적용한 결과, AI와 도구가 실행하는 장치는 돌았고 사람이 실행하는 장치는 돌지 않았다. explain-back은 대기 11건에 완료 0건, weekly-audit는 0회였다. AI는 12분에 약 1,150줄을 만들었고, 사람이 따라가지 못해 개발을 멈췄다.

사용자가 짚은 원인은 두 가지다. AI가 내는 문서가 너무 많다. AI가 중간부터 결정해서 이전 사고 흐름을 알 수 없다.

| 질문 | 결정 | 누가 |
|---|---|---|
| 질문 지도가 기존 설계 문서를 대체하나 | 사람이 읽는 문서는 질문 지도 1장. 설계 메모와 ADR은 기록용으로 남기고 지도의 답을 옮겨 쓴다 | 사용자 |
| 구현 뒤 이해 확인 | 두 줄 설명을 예측 질문 1개로 바꾼다. 강제하지 않고 대기 수만 보여 준다 | 사용자 |
| "추천대로"로 넘긴 결정 | 지도에 위임을 표시하고 explain-log 대기에 넣는다 | 사용자 |
| AI가 한 번에 만드는 코드 양 | 제한을 두지 않는다 | 사용자 |
| AI가 새로 만든 방식 | 다른 코드가 따라 쓸 패턴만 질문 지도에 올려 사람이 정한다. 파일 안에서 끝나는 도우미는 커밋에 한 줄 | 사용자 |
| 품질 추세 점검 | 주 1회 대신 단계가 끝날 때 한 번 (phase-audit) | 사용자 |
| 프로젝트 안의 규칙 사본 | 프로젝트에서 고쳐도 된다. 끝나면 원본으로 가져온다 | AI 제안, 사용자 확인 |

사후에 "왜 그랬는지 적게" 하는 방법은 2절의 이유로 쓰지 않았다. 대신 설계 전에 질문을 순서대로 내서, 사람이 같은 순서를 걷게 했다.
